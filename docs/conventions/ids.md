# ID conventions

- **Status:** Accepted
- **Date:** 2026-09-24

Every entity in PATHS has one permanent ID. IDs are hand-written in `data/` and appear in edges, citations, API responses and URLs, so they must be **readable, permanent, collision-free and spoiler-safe**.

## 1. Format

```
<kind>_<slug>
```

```
character_eren_yeager    faction_survey_corps    event_fall_of_wall_maria    titan_attack
```

- Lowercase ASCII letters `a–z`, digits `0–9`, and single underscores between words.
- The `<kind>` prefix must match the entity's `kind` field.
- Keep the slug short — at most about five words.

Pattern (enforced by the Zod schema in Phase 1):

```
^(character|titan|event|location|faction|arc|memory)_[a-z0-9]+(_[a-z0-9]+)*$
```

**Why readable slugs, not UUIDs:** the data is written by hand. `character_eren_yeager` can be typed, reviewed in a diff, and searched; a UUID cannot. UUIDs suit IDs generated by a database — ours are authored by a person.

## 2. Entity kinds

| Kind        | Represents                                                             |
| ----------- | ---------------------------------------------------------------------- |
| `character` | An individual person, in any form (human or Titan)                     |
| `titan`     | One of the Nine Titan powers                                           |
| `event`     | Something that happens at a point or over a span of in-universe time   |
| `location`  | A place — territory, settlement, structure, or other place             |
| `faction`   | An organized group — military, government, movement, family line, etc. |
| `arc`       | A PATHS-defined story arc (see `canon-and-sources.md` §9)              |
| `memory`    | **Provisional** — finalized in `model/relationships.md` (Step 11)      |

**Edges have no hand-written IDs.** An edge is identified by the tuple **(source, type, target, start date)**. The seed script derives its database ID from that tuple, and the validator rejects duplicate tuples.

## 3. Kind boundaries

Rules for things that could fit more than one kind:

- **A Titan form is not a separate entity.** `titan_*` is reserved for the Nine Titan powers (`titan_attack`, `titan_founding`, `titan_war_hammer`, …). A shifter or a pure Titan is the `character`, appearing in Titan form.
- **Land vs. power.** A nation's territory is a `location`; its government or military is a `faction` — e.g. `location_marley` vs. `faction_marleyan_military`.
- **The Walls are `location`s** — e.g. `location_wall_maria`.
- **Non-physical places are `location`s** — e.g. `location_paths`.
- **A family or bloodline** that acts as a group is a `faction`; blood relationships between individuals are edges between `character`s.

When a new ambiguous case appears, decide it once and add it to this list.

## 4. Building a slug

1. Start from the entity's name **as defined in §5**.
2. Transliterate to ASCII (drop accents and diacritics).
3. Lowercase.
4. Remove punctuation — `Eren's` → `erens`.
5. Replace spaces and hyphens with `_`; collapse repeats.
6. Drop a leading "the" — `The Rumbling` → `rumbling`.

**Events** are named after what happened, never after where it appears in the manga: `event_battle_of_trost`, not `event_ch10`.

**Clashing names:** when two entities would produce the same or confusingly similar slugs, **both** get a qualifier — neither keeps the bare name, because a bare name implies it's the "main" one:

```
character_ymir_fritz
character_ymir_104th
```

## 5. Spoiler safety

IDs are visible in URLs, API responses and bookmarks. An ID must never reveal something the reader hasn't reached yet.

**Rule: an ID is based on how the reader first encounters the entity** — the name or description used at its earliest appearance in reading order — never on a later reveal.

- Historia Reiss is first introduced as Krista Lenz → `character_krista_lenz`. Her **display name** can still read "Historia Reiss" for readers past the reveal; display names and aliases carry their own revealed-in chapter (see `model/spoilers.md`).
- A character first seen only as an unnamed Titan gets an ID describing that appearance (e.g. `character_smiling_titan`), not their later-revealed name.
- The same applies to events: name them by what the reader sees when the event first appears, not by what is later revealed about it.

Some IDs will read oddly to someone who knows the whole story. That is the accepted cost of never leaking a spoiler through a URL.

## 6. Permanence

- **Until the first public deployment (Phase 3):** IDs may be renamed freely — nothing links to them yet.
- **After the first public deployment:** IDs are **permanent** and **never reused**.
  - If an entity is merged, split or removed, its old ID is recorded in `data/id-redirects.yaml` (`old_id: new_id`, or `old_id: null` for removed entities) so existing links still resolve.
- Changing a display name **never** changes an ID.

## 7. Enforcement

The Phase 1 validator (`pnpm validate`) checks that:

- every ID matches the pattern in §1;
- every ID's prefix matches its `kind`;
- no two entities share an ID;
- every reference in `data/` points to an existing ID (or to a redirect);
- no two edges share the same (source, type, target, start date) tuple;
- no redirect points to another redirect or to a missing ID.
